# AL-thmany 4.0 Stability & Smart Automation Design

## Goal
Produce a safer, more deterministic AL-thmany release from the integrated Sender + Extractor source without removing current capabilities. The release must prevent concurrent WhatsApp UI controllers, reduce false group discovery, improve recovery/checkpoint behavior, make regression checks reproducible, and package a build-ready source tree with explicit verification evidence.

## Existing Architecture
The application is a single Android app (`com.althmany.groupmanager`) containing two major runtime families:

1. Sender / Join automation under `com.althmany.groupmanager`, using its own Accessibility and Shizuku runtimes.
2. Extractor workspace under `com.althmany.extractor`, providing extraction, invite scanning, publishing, persistence, export, and an additional Accessibility service.

Both families can control the same WhatsApp UI. The Extractor currently has a process-local `RuntimeOperationCoordinator`, and its UI checks whether the Sender batch is active. The reverse path is not equivalently enforced at the Sender runtime boundary, so UI-only checks are insufficient.

## Design Decisions

### 1. Shared process-local UI ownership gate
Extend `RuntimeOperationCoordinator` with a `SENDER` operation and an idempotent `ensureOwned()` path for persisted Sender recovery. Sender will acquire ownership before starting a batch and release ownership on stop/completion/reset. Extractor start/resume/sync/scan/publish entry points will also check the Sender persisted state directly so notification or non-UI entry paths cannot bypass the guard.

The existing strict `tryAcquire()` behavior remains unchanged for Extractor operations to prevent same-operation re-entry such as sync + extraction.

### 2. Sender recovery ownership
A Sender batch may survive Android service recreation while the process-local gate does not. `QuickJoinAccessibilityService` will re-establish SENDER ownership before performing active automation. If another operation owns the UI, Sender will not execute actions and will record a diagnostic rather than racing the other engine.

### 3. Group discovery hardening
Extract the title exclusion rules from the Android adapter into a pure Kotlin `ConversationTitlePolicy`. It will reject toolbar/filter/system actions including Arabic and English variants of:

- Manage groups / إدارة المجموعات
- New group / مجموعة جديدة
- Archived / المؤرشفة
- Communities / المجتمعات
- Search / بحث
- New chat / دردشة جديدة
- Group info / معلومات المجموعة
- Add group / إضافة مجموعة
- Create community / إنشاء مجتمع

`WhatsAppUiAdapter` will delegate title validation to this policy. This makes the rule testable without Android and reduces accidental persistence of UI controls as chats/groups.

### 4. Persistent checkpoint safety
Preserve current checkpoint/database behavior. Do not cache `AccessibilityNodeInfo` across UI changes. Continue storing only stable metadata, group IDs/names, checkpoint tokens/signatures, and access-method hints.

### 5. Regression harness reliability
Split the slow monolithic Pure Kotlin regression compile into deterministic compile/run phases and add a focused 4.0 stability regression entry point for the new ownership and group-title policies. Existing integrated Extractor pure checks remain part of verification.

### 6. Build reproducibility
Add Gradle wrapper metadata/scripts where possible without fabricating a downloaded wrapper JAR. The source package will include a wrapper bootstrap helper and GitHub Actions build path. If the local environment lacks Android SDK/Gradle, the delivery report will explicitly distinguish source/pure-test success from full Android APK build status.

### 7. Versioning and documentation
Set the app version to 4.0.0 with an incremented versionCode. Update README/CHANGELOG with the stability changes and known environment limitations. Existing features are retained.

## Error Handling

- A conflicting operation must fail closed with a visible/diagnostic reason; it must not silently proceed.
- Ownership release must be idempotent.
- Sender service recreation may reclaim ownership only when no other operation owns the UI.
- Group-title filtering errs toward exclusion for known system controls but must not reject ordinary group names merely because they contain common words.
- No unbounded recovery loops are introduced.

## Verification Gates

1. Source validators pass.
2. Integrated Extractor pure checks pass.
3. New 4.0 stability pure checks pass.
4. Existing Pure Kotlin regressions pass within an increased deterministic timeout or are split so the failing phase is identifiable.
5. XML resources/manifest parse cleanly.
6. If Android SDK/Gradle are available: unit tests, lint, and `assembleDebug` pass.
7. Packaging contains no temporary build/test directories and preserves all source files.

## Non-Goals

- No bypass of WhatsApp restrictions or rate limits.
- No hidden automation or anti-detection behavior.
- No direct WhatsApp database access.
- No redesign of the entire UI.
- No destructive rewrite of the existing Sender or Extractor architecture.
